# Terrarium 컨셉 정리

> 제품명: **Terrarium (테라리움)**
> 개발 코드: 작성 프로그램 **Bethlehem** / 내보낸 문서 **Manna**

---

## 1. 왜 만드는가

기획자들이 바이브 코딩을 이용해 high-fi 버전 화면정의서를 멋있게 만들어도, 안에 어노테이션을 할 수 없으니, 결국 화면을 일일히 캡처해가며 다시 ppt로 전달하고, 회의 때 나오는 내용도 캡처 후 ppt 붙이고 텍스트 쓰기를 반복해야 한다.

닷넷이나 유니티 등등 C#으로 만든 실행 프로그램이야 어쩔 수 없다 쳐도, 웹 문서가 이렇게 편리하게 뚝딱 나오는 시대에 너무 원시적이다.

화면은 AI가 만들어주고, AI로 몇 분만에 고쳐진다. 그런데 사람과 사람이 문서로서 화면을 주고받으려 할 때, 화면에 대한 설명과 요청은 여전히 캡처 이미지에 묶여 있다. 화면을 한 번 고치면 캡처를 다시 뜨고, 슬라이드에 다시 붙이고, 박스를 다시 치고, 번호를 다시 맞춰야 한다. 화면은 살아서 움직이는데, 그 화면을 설명하는 문서는 정지된 그림이다. 이 불일치가 문제점(병목)을 만든다.

게다가 캡처로는 화면이 "어떻게 움직이는지"를 전달할 수 없다. 정렬이 되는지, 탭이 넘어가는지, 차트가 어떻게 갱신되는지는 결국 말로 설명하거나, 대면으로 만나 화면을 보여주며 미팅을 해야 한다. high-fi로 프로토타입을 만들어 두고, 전달 단계에서는 다시 low-fi로 내려간다.

피그마 같은 디자인 도구도 답이 되지 못한다. 피그마의 프로토타입은 그려진 프레임을 클릭으로 이어 붙인 것이지, AI가 이미 코드로 만들어 둔 실제 화면이 아니다. 동작하는 화면을 전달하려고 그 화면을 디자인 도구에 다시 그리는 것은 일을 거꾸로 하는 셈이고, 실제 데이터로 정렬되고 갱신되는 동작은 그 안에서 재현되지도 않는다. 코드로 화면을 고치면 피그마 쪽은 따라오지 않으니 결국 두 벌을 맞추는 일이 다시 생긴다. 또한 코멘트를 보고 답하려면 받는 사람도 계정과 접근 권한이 있어야 하고 클라우드에 올려야 하므로, 고객사나 외부 이해관계자와 가볍게 주고받기에도 부담이 있다.

테라리움(Terrarium)을 하나 개발해 보자.

유리 용기 안에 살아 있는 생태계를 통째로 담아 주고받는 것처럼, 동작하는 화면을 문서 안에 완결된 채로 담는다는 콘셉트로. 프로그램 이름은 테라리움으로, 내보낸 문서는 "테라리움 파일"로.

## 2. 빵집과 빵

이 프로젝트에서 하고자 하는 일은 빵집과 빵의 관계로 설명된다.

**빵집(Bethlehem)** : 웹은 문서다. 빵집은 문서를 굽는 곳이다. 프로토타입을 받아들이고, 어노테이션을 달고, 버전을 관리하고, 돌아온 의견을 합치는 모든 무거운 작업은 빵집에서 이루어진다. 설치형 프로그램이며, 편리한 부가기능을 추가하며 맛있는 빵을 만들기 위한 그릇이다.

**빵(Manna)** : 빵은 빵집에서 구워져 나온 문서다. HTML 파일 하나이고, 받은 사람은 아무것도 설치하지 않고 더블클릭만 하면 연다. 만나가 주어지듯이, 받는 사람에게는 아무것도 요구하지 않는 문서다. 사람들끼리 의견의 교환이 이루어진다.

핵심은 빵집이 없어도 빵은 먹을 수 있어야 한다. 빵은 그 자체로 완결되어 있다. 화면이 재생되고, 어노테이션이 보이고, 수신자가 답글을 달고, 체크를 하고 저장해서 돌려보내는 것까지 문서 안에서 끝낸다. 빵집은 빵을 맛있게 굽기 위해 존재한다.

## 3. 핵심 컨셉 : 문서의 문서

만나는 화면정의서를 품은 문서다. 바이브 코딩으로 만든 HTML 화면을 건드리지 않고 그대로 안에 담고, 그 바깥을 문서의 틀이 다시 감싼다. 원본 화면은 첨부물처럼 보관되고 열 때마다 안에서 실제로 실행된다.

```
OHT모니터링_화면정의서_v1.2.html   (Manna)
├── 뷰어 / 편집 코드          화면 표시, 마커, TODO 패널, 답글, 저장
├── 문서 데이터 (JSON)
│    ├── 문서 정보            제목, 프로젝트, 버전, 변경 이력
│    ├── 화면 목록
│    │    └── SCR-003 설비정보 확인
│    │         ├── 화면 패키지 v1, v2 ...   (원본 HTML과 data/ 등 폴더째 보관)
│    │         └── 어노테이션 목록           (요소 지문, 번호, 내용, 상태, 답글)
│    └── 참여자               이름, 역할
└── (끝)
```

원본 화면이 오염되지 않아 언제든 꺼내서 다시 쓸 수 있고, 문서 데이터는 json 등 잘 쓰이는 포맷으로 필요하면 별도로 주고받을 수 있다.

```
┌──────────────────────────────────────────────────────┐
│ 툴바: 화면 선택 · 버전 · 모드 전환 · 저장            │
├───────────────────────────────────┬──────────────────┤
│                                   │                  │
│          품긴 화면 (실제 동작)     │    TODO 리스트    │
│          ① ② ③ 마커 표시           │    어노테이션     │
│                                   │    답글 · 상태    │
│                                   │                  │
└───────────────────────────────────┴──────────────────┘
```

## 4. 품을 수 있는 화면

**라이브 패키지** : 파일만으로 완결된 프로토타입을 폴더째 담는다. HTML, CSS, JS, 데이터 파일, 이미지로 구성된 화면이 여기에 해당하며, 문서 안에서 실제로 재생되고 받는 사람도 똑같이 조작할 수 있다.

**스냅샷** : 외부 URL 페이지는 다른 도메인의 내부를 읽을 수 없다는 브라우저 정책 때문에 그대로 품어서는 어노테이션을 달 수 없다. 그래서 작성 시점의 HTML과 리소스를 저장해 고정한 상태로 담는다. 서버와 주고받던 동작은 멈추지만, 서버가 필요 없는 화면 내 동작은 살아 있을 수 있다. 시간이 지나면 바뀌거나 사라질 수 있는 외부 페이지를 기록으로 남긴다는 점에서 오히려 화면정의서에 적합한 면도 있다.

**움직임 클립** : 스냅샷으로 살릴 수 없는 움직임은 Bethlehem에서 짧게 녹화해 영상으로 담는다. 움짤 수준의 흐름을 보여주는 용도이며, 화면 전체나 특정 어노테이션에 첨부한다.

### 품을 수 없는 것 : 이것은 빵이 아니다

동작하는 데 실행 중인 서버가 필요한 화면, 백엔드 API로 데이터를 받아오는 화면, PHP나 서버 렌더링처럼 요청 시점에 HTML이 만들어지는 화면, 실제 장비와 WebSocket이나 MQTT로 연결된 실시간 화면은 문서에 담을 수 없다. 빌드 전의 React나 TypeScript 소스도 그대로는 안 되며 빌드 결과물을 담아야 한다. 기획자가 화면정의서용으로 만드는 프로토타입은 대부분 더미 데이터나 추출해 둔 데이터로 돌아가므로 이 제약에 거의 걸리지 않는다.

## 5. 어노테이션과 TODO

어노테이션은 화면의 DOM 요소에 붙는다. 개발자 도구의 요소 선택처럼 화면 위에서 요소를 찍으면 박스로 하이라이트되고 번호 마커가 붙으며, 오른쪽 패널에 같은 번호의 항목이 생긴다. 요소 단위로 잡기 어려운 경우를 위해 자유 영역 박스도 그릴 수 있다.

각 어노테이션은 화면정의서의 설명이면서 동시에 TODO 항목이다. 상태, 유형, 담당자, 답글 스레드를 가지며, 기획자와 개발자와 이해관계자가 그 위에서 확인하고 회신하고 완료를 표시한다. 수신자도 Manna 안에서 직접 새 어노테이션을 달 수 있으며, 수신자가 단 항목은 작성자 이름과 함께 기록되어 빵집에서 병합할 때 원래 목록에 합쳐진다. 화면 새 버전에 맞춰 어노테이션을 다시 붙이는 재부착 작업은 빵집에서 한다. 어노테이션이 붙은 요소의 크기, 색상, 폰트 같은 속성은 자동으로 함께 보여줄 수 있어, 개발자는 별도 디자인 도구 없이도 필요한 정보를 얻는다.

## 6. 주고받는 흐름

기획자는 빵집에서 빵을 만들고 화면 패키지를 등록한 뒤 어노테이션을 달아 만나로 내보낸다. 수신자는 받은 만나(HTML)를 브라우저에서 열어 화면을 직접 조작해보고 어노테이션을 읽고, 답글을 달거나 체크박스 상태를 바꾸거나 새 어노테이션을 단 뒤 저장해서 돌려보낸다. 기획자는 돌아온 문서들을 빵집에서 열어 원본에 병합한다. 화면을 고쳐야 하면 새 버전 화면을 넣고, 어노테이션이 새 화면에 다시 붙은 것을 확인한 뒤 다시 내보낸다. 이전 버전 화면은 문서 안에 남아 변경 전후를 비교할 수 있다.

서버는 어디에도 없다. 문서 파일 자체가 오가는 단위이며, 메일이든 메신저든 파일을 주고받는 경로만 있으면 된다.

| 구분 | Bethlehem (빵집) | Manna (빵) |
|---|---|---|
| 형태 | Electron 설치형 프로그램 | HTML 파일 하나 |
| 사용자 | 작성자(기획자) | 수신자(개발자, 고객사, 이해관계자) 및 작성자 |
| 화면 | 패키징, 스냅샷, 움직임 녹화, 버전 관리 | 품은 화면 재생, 조작 |
| 어노테이션 | 작성, 재부착, 재지정 | 열람, 작성, 답글, 상태 체크 |
| 협업 | 돌아온 문서 병합 | 저장 후 회신 |
| 확장 | 부가기능 추가 및 업데이트 배포 | 자기완결적, 설치 불필요 |

## 8. 결정 사항과 검토 사항

**수신자 편집 범위 : 어노테이션 추가까지 허용한다.** 수신자도 답글과 상태 체크뿐 아니라 새 어노테이션을 달 수 있다. 따라서 Manna 안에도 요소 선택, 마커 생성, 자유 영역 박스 기능이 들어간다.

**작성자 식별 : 이름 입력 방식이 유력하다.** 서버가 없으므로 수신자가 처음 열 때 이름을 한 번 입력받아 어노테이션, 답글, 체크에 남긴다.

**Manna 안에서의 저장 방식.** 브라우저로 연 웹페이지는 보안상 내 PC의 파일을 직접 고쳐 쓸 권한이 없다. 그래서 수신자가 Manna에서 저장 버튼을 눌렀을 때 변경 내용을 파일로 남기는 방식이 브라우저마다 다르다. Chrome과 Edge는 사용자가 허락하면 파일에 쓸 수 있는 기능이 있어, 처음 저장할 때 대상 파일을 한 번 지정해 주면 그 뒤로는 일반 프로그램처럼 같은 파일에 덮어쓴다. Firefox와 Safari는 이 기능이 없어 저장할 때마다 다운로드 폴더에 새 파일(예: 화면정의서_v1.2_홍길동.html)이 생기고, 그 파일을 돌려보내면 된다. 어느 쪽이든 결과는 변경 내용이 들어간 HTML 파일이므로 주고받는 데는 차이가 없다.

**라이브 패키지의 지원 범위.** 정적 파일 참조, fetch 요청, 실행 중 동적으로 추가되는 스크립트는 문서 안에 보관된 파일로 연결해 줄 수 있다. 다음 두 가지는 빵집에서 패키징할 때 별도 처리가 필요하다.

모듈 구조는 JS 코드를 여러 파일로 쪼개 `import { drawChart } from './chart.js'`처럼 서로 불러 쓰는 방식으로, Vite 같은 도구로 빌드한 결과물이 대개 이렇게 여러 조각 파일로 나뉜다. 이 import는 브라우저가 내부적으로 직접 처리하므로 스크립트 태그나 fetch를 가로채는 방식으로는 끼어들 수 없고, 더블클릭으로 연 파일 상태에서는 브라우저가 모듈 방식 스크립트 자체를 막는다. 빵집에서 패키징할 때 쪼개진 파일들을 하나로 합쳐(번들링) 넣는 것으로 해결한다.

Web Worker는 무거운 계산을 화면이 멈추지 않게 뒤에서 따로 돌리는 기능으로, 그 코드를 `new Worker('worker.js')`처럼 별도 파일로 불러온다. 같은 이유로 그대로는 동작하지 않지만, 빵집에서 문서 안의 코드로 바꿔 연결해 주면 대부분 해결된다. 화면정의서용 프로토타입에서는 드물게 쓰인다.
