# play/ — 데이터 매핑

## 미국 전시회 데모 화면 — 2026-09-05 개정

기준 문서: 「미국 전시회 데모 구성안 (개발 전달용)」 2026-09-05.
**`index.html` 이 그 화면입니다.** 별도 파일을 두지 않았습니다.

앞선 개정에서 맞춰 둔 rcis(제품) 화면 구성 — 상단 바, 경고 감지 · OHT 건강도 ·
AI 모니터링 에이전트 · 미니맵, 보조 창 — 은 그대로 살아 있고,
그 위에 데모 구성안의 3분할과 BAD/GOOD 비교를 얹었습니다.

### 화면 둘 — FAB 조망 · 설비정보 확인

탭은 둘입니다. 상세 맵은 탭이 아니라 **FAB 안으로 들어간 화면**입니다.

```
  [ FAB ]  [ 설비정보 확인 ]         ← 탭
     │
     ├── FAB 조망 (처음 화면) — 구역 4개 · ★ BAY-4 클릭
     │        ↓                           ↑  ← FAB 조망
     └── BAY-4 상세 맵 — 실시간 운행 + 에이전트 + BAD/GOOD 비교
```

상세 맵을 별도 탭으로 두면 '팹 전체' 와 '한 구역' 이 형제처럼 보여, 들어갔다 나오는
관계가 화면에서 사라집니다. 그래서 탭을 없애고 맵 좌상단에 **`← FAB 조망 · BAY-4`**
하나를 뒀습니다. FAB 탭은 상세 맵을 보는 동안에도 켜져 있습니다 — '그 안에 들어와
있다' 는 표시입니다.

#### 상세 맵 (BAY-4)

```
┌───────────────────────┬──────────────┬──────────────────┐
│                       │ ① 경고 감지   │ 최적 계획 수립 ⟳반복│
│                       │      ↓       ├──────────────────┤
│  3D 확대 · 실시간 운행  │ ② OHT 건강도 │  BAD CASE        │
│  (비교 재생과 비연동)   │      ↓       ├──────────────────┤
│  클릭 → 보조 창        │ ③ AI 에이전트│  GOOD CASE       │
│                       │      ↓       │                  │
│                       │ ④ 미니맵     │                  │
└───────────────────────┴──────────────┴──────────────────┘
```

- **① 경고 감지**(= Alerts) · **② OHT 건강도**(= Fleet Health) · **③ AI 모니터링 에이전트**
  (= AI Monitoring Agent) · **④ 미니맵** — 이름과 표현은 제품(rcis) 그대로입니다.
- 구성안 §2.3 대로 상단의 **스파크라인 · 데이터 수집 영역은 통째로 뺐습니다.**
- **② 건강도의 오각형은 그대로 두고 값만 전 차량 평균**으로 냅니다(`fleetHealth`).
  각 축은 '그 동작을 얼마나 제 속도로 해내는가' 를 0~100 으로 말하고, 관측이 없는 축은
  제품과 같이 `- 데이터 없음` 입니다.
- 중앙 패널은 전부 **좌측 실시간 뷰의 시계**를 봅니다. 비교 타임라인을 따르게 하면
  미니맵과 건강도가 '지금 현장' 이 아니라 가정 시나리오를 가리켜 두 시제가 섞입니다.
- 비교 두 장은 **자기 컨트롤만** 따릅니다(구성안 §5.2) — 재생/정지 · 1x/2x/4x · 스크럽,
  그리고 **반복**. 반복을 켜 두면 끝난 뒤 처음부터 다시 돌아 부스에서 손대지 않아도 됩니다.
- **하단 플레이바**는 제품(rcis)의 LIVE / HISTORY 그대로입니다. HISTORY 로 넘기면
  화면 전체 폭 아래에서 **3분 시나리오**를 훑습니다 — 트랙 배경이 정상(회색) → S-1(앰버)
  → S-1+S-2(빨강)로 칠해지고, 두 이상 지점에 마커가 섭니다. 이 바는 **좌측 실시간 뷰**를
  움직입니다(우측 비교는 §5.2 대로 따로 돕니다). 이전/다음 버튼은 이상 발생 지점으로 점프,
  배속 0.5x~4x, 좌우 방향키 0.1초(Shift 1초) 스크럽입니다.
  **반복** 버튼을 켜 두면 끝에서 처음으로 돌아가 계속 재생됩니다 — 비교 열의 반복과 별개로
  동작하므로, 좌측 실시간 뷰와 우측 비교를 각각 상시 재생으로 걸어 둘 수 있습니다.

### FAB 조망 — 처음 나오는 화면

사이드 패널 없이 팹 한 장이 화면을 채우고, 최소한의 글자(범례 · 상태 요약)만 얹습니다.
2.5D 아이소메트릭이며 상세 맵과 같은 투영·같은 시각 언어를 씁니다.

```
        BAY-2              BAY-3
       ┌────────┐         ┌────────┐
       └──┬──┬──┘         └──┬──┬──┘
   ════════╪══╪═══════════════╪══╪════════   ← 간선(inter-bay) 루프
       ┌──┴──┴──┐         ┌──┴──┴──┐
       │        │         │  ★     │
       └────────┘         └────────┘
        BAY-1              BAY-4 ★
```

- 실제 팹의 **intra-bay / inter-bay** 구조를 씁니다. 가운데를 가로지르는 간선 루프에
  네 구역이 위아래로 매달리고, 각 구역의 **분기부 A(진입) · 합류부 B(반출)** 가 짧은
  스퍼로 간선에 물립니다. 그래서 트랙이 전부 이어져 있습니다.
- **★ BAY-4 하나만 클릭 가능**하고, 그것이 곧 상세 맵이 보여 주는 구역입니다.
  클릭하면 그 구역으로 들어갑니다. 호버하면 판이 밝아집니다.
- ★ 구역의 OHT 5대는 **상세 맵과 같은 시뮬레이션 프레임**을 읽습니다 —
  두 화면의 차량 위치가 어긋날 수 없고, 이상 구간(빨강)도 같이 보입니다.
- 나머지 세 구역도 같은 밀도로 살아 있습니다(구역당 4~6대). 클릭만 안 됩니다.
- **구역 간 반송 OHT**(파랑) 가 간선을 돌다 진입구를 지나칠 때 확률로 스퍼를 타고
  내려와 구역을 한 바퀴 돌고 반출 스퍼로 나갑니다 — OHT 가 구역을 드나드는 장면입니다.
  한 대가 특정 구역만 노리게 두면 한 바퀴(70초)에 한 번밖에 안 들어가 거의 안 보입니다.
- **AMR**(주황) 은 바닥(z=0) 통로를 왕복합니다. 천장 반송과 층이 다르다는 것이 보입니다.
- 구역 간 반송 차량은 색을 달리해 그 구역에 **배정된** 차량과 구분합니다 —
  상세 맵이 다루는 것은 배정된 5대뿐이기 때문입니다.
- 구역 판은 바닥이 아니라 **레일 높이**에 얹었습니다. 바닥(z=0)에 두면 아이소에서
  천장 트랙이 위로 밀려 올라가 판과 어긋나 보입니다.
- FAB 탭의 주변 교통(다른 구역·구역 간 반송·AMR)은 연출이라 시드를 고정하지 않습니다.
  측정 대상인 모니터링·비교 시뮬레이션만 결정론적입니다.

### 상세 맵이 보여 주는 '연결된 트랙'

이 구역은 팹 안에 떠 있는 것이 아니라 간선(inter-bay) 루프에 물려 있습니다.
FAB 조망에서 보이는 그 스퍼의 **구역 쪽 끝 9 m** 를 상세 맵에도 그립니다 —
분기부 A 로 들어오고 합류부 B 로 나가는 길이 실제로 있다는 것이 보여야 합니다.
스퍼는 끝으로 갈수록 옅어져 '화면 밖으로 계속 간다' 로 읽히고, `← 간선에서 진입` /
`간선으로 반출 →` 라벨이 붙습니다.

**간선 본선도 함께 그립니다.** 통과 차량이 허공에서 나타나면 안 되니, 구역 옆을 지나가는
본선 레일을 양 끝이 페이드되게 깔고 그 위로 들어오게 했습니다. 경로는
`본선 16 m → 진입 스퍼(A) → 상부 루프 한 바퀴 → 반출 스퍼(B) → 본선 16 m` 입니다.

그 길로 **구역 간 반송 OHT**(파랑, `구역 간 반송` 라벨)가 42초 주기로 세 대 들어옵니다.
미니맵에도 본선·스퍼와 함께 표시됩니다.

본선·스퍼는 **우측 비교 두 장에도 같이 그립니다** — 같은 구역으로 읽혀야 하기 때문입니다.
다만 통과 차량은 비교에 그리지 않습니다. 비교는 '이 구역 5대를 두 배차로 돌렸을 때' 를
재는 통제된 실험이고, 그 5대만 시뮬레이션에 들어 있습니다.

차량 이름표는 **차체를 다 그린 뒤 두 번째 패스로** 얹습니다. 한 패스로 하면 차량이 몰릴 때
`구역 간 반송` 라벨이 배정 차량 이름을 덮어 둘 다 못 읽게 됩니다. 배정 차량을 먼저 놓고
겹치는 통과 차량 라벨은 접습니다 — 이름이 곧 정보인 쪽을 살립니다.

- 이 차량들은 **이 구역에 배정된 5대가 아닙니다.** 색과 라벨을 달리해 구분합니다.
- **표시 전용입니다** — BAD/GOOD 비교 시뮬레이션에는 들어가지 않습니다. 비교는
  '이 구역 5대를 두 가지 배차로 돌렸을 때' 를 재는 통제된 실험이고, 통과 차량은 두 케이스에
  똑같이 있으므로 비교 자체를 흔들지 않습니다.
- 위치는 실시간 시계에서 바로 계산합니다 — 상태를 두지 않으니 되감아도 어긋나지 않습니다.

### 설비정보 확인 탭 (옛 '데이터 분석')

RAW 집계·박스플롯이 중심이던 탭을 **설비 진단**으로 갈아 엎었습니다. 집계·시각화는 만드는
쪽에 필요한 화면이고, 쓰는 쪽은 KPI 와 조치에 눈이 갑니다. 이상감지 솔루션을 만드는
입장에서 넣었던 화면이라 고객 관점에서는 설 자리가 없었습니다.

```
┌──────────────┬──────────────────────────────────────────┬──────────────┐
│ ① 설비 리스트 │ ② 설비 진단                [종합 스코어] │ ③ RAW        │
│  OHT 5대      │ ┌ 부위 도해 ┐┌ 미니캠 ┐│              │ │  고른 차량의  │
│  레일 7구간   │ │ 2.5D      ││ 추적   ││  차량        │ │  탑재 채널만  │
│              │ └───────────┘└────────┘│  데이터시트   │ │  (레일이면    │
│              │ ┌ 개별 퍼포먼스 오각형 ┐│  API 610 서식 │ │   비활성)     │
│              │ ├ 고른 부위 스코어·근거 ┤│  PAGE 1~4    │ │              │
│              │ ├ 스펙 / 검사 / 정비 ──┘│  + 출처       │ │              │
└──────────────┴──────────────────────────────────────────┴──────────────┘
        왼쪽 절반 — 그림 둘을 나란히, 그 아래로 진단을 쌓는다
        오른쪽 절반 — 데이터시트 한 장 (칸 높이에 맞춰 본문만 스크롤)
```

- **좌: 설비 리스트** — OHT 5대와 레일 7구간. 상세 맵에 없는 목록이라 여기 둡니다.
  위치·상태는 맵과 같은 시뮬레이션 프레임에서 읽습니다.
- **가운데 왼쪽 절반** — 위에 **부위 도해**(2.5D · 클릭 가능)와 **미니캠**(그 차량 추적)을
  반씩 나란히, 그 아래로 **개별 퍼포먼스 오각형 → 고른 부위의 스코어·근거 → 스펙 →
  검사 이력 → 정비 이력** 을 하나씩 쌓습니다.
- **가운데 오른쪽 절반** — **차량 데이터시트**. 아래 절을 보십시오.
- **구간을 고르면** 같은 자리가 [최근 통과 영상][미니캠] + 구간 상태 · 구간 상세로 바뀌고,
  오른쪽은 **RAIL AND TRACK 구간 데이터시트**가 됩니다.
- **우: RAW** — 고른 차량에 실린 채널만. 레일 구간을 고르면 비활성입니다(레일에는
  탑재 센서가 없고, 구간 상태는 차량이 지날 때의 값으로만 압니다).

#### 차량 데이터시트 — API 610 / ISO 13709 서식

따라갑니다), 스토커 `STK-BAY4-01`. 넷 다 ■ ATTACHED 입니다.

주의 한 가지 — 시트의 최대 주행 속도는 **5 m/s(벤더 공개 사양)** 이고 이 데모의 운전
속도는 **4.0 m/s** 입니다. 두 값을 나란히 두면 오해하므로 PERFORMANCE · TRAVEL 에
`OPERATING SPEED, THIS UNIT` 줄을 따로 넣었고, 부위 스펙 카드도 '운전 속도 (이 데모)'
로 적습니다.

구간을 고르면 같은 서식으로 **RAIL AND TRACK 구간 시트**가 한 장 뜹니다 — 구간 제원
(길이 · 곡선 반경 · 제한 속도), 레일 구조와 공차, CONDITION MONITORING. 레일에는 고정
센서가 없으므로 그 값도 **차량이 지날 때 읽은 것**이라고 시트 안에 적어 둡니다.

#### 도해에서 뺀 것 · 넣은 것

지시선 이름표(`구동부 87/100`)를 **뺐습니다.** 그림이 글자에 묻혔고, 누르면 옆에서
이름·스코어·근거를 다 말하므로 도해 위의 글자는 중복이었습니다. 남긴 신호는 셋뿐 —
고른 부위가 밝아지고 나머지가 한 톤 물러나는 것, 상태가 나쁜 부위의 테두리 색,
프레임 아래 캡션 한 줄.

레일과 천장은 프레임 끝까지 뻗어 잘려 나갑니다. 레일은 원래 끝이 보이지 않는
물건이고, 배율은 차량 경계로만 잡아야 차량이 점이 되지 않습니다.

차체 비례는 **스펙 시트를 따릅니다** — 1,050 × 720 × 620 mm(길이:폭:높이
1.46 : 1 : 0.86). 눈대중으로 납작하게 세웠을 때는, 트랙 위에 얹으면 진행 방향이
사선일 때 상판만 보이는 '테이블' 로 읽혔습니다.

클릭 판정은 **픽셀로** 합니다. 부위별 사각형으로 판정하면 차체의 먼 쪽 윗면과
구동부의 사각형이 화면에서 겹칩니다(세로가 (x+y)/2−z 라 그렇습니다). 같은 그림을
부위 색으로 한 번 더 그려 두고 그 픽셀을 읽으면 휠 하나도 정확히 잡힙니다.

#### 미니캠 — 도해 옆, 같은 차량

롤러코스터 타이쿤에서 탈것을 고르면 카메라가 따라붙던 그 창입니다. **영상이 아니라
같은 시뮬레이션의 확대**이고, 씬은 상세 맵과 같은 렌더러로 그립니다 —
'확대만 다른 같은 세계' 여야 보는 사람이 저 화면의 저 차량으로 잇습니다.

- 정지 도해 옆에 두면 한 화면에서 **제원(도해)과 지금 그 차량이 하는 일(미니캠)** 이
  나란히 읽힙니다. 둘이 합쳐 가운데 패널의 왼쪽 절반을 반씩 나눠 씁니다.
  미니캠 칸은 하나뿐이고, 차량을 고르면 차량 옆으로 구간을 고르면 구간 옆으로
  옮겨 붙습니다.
- 쫓는 차량 한 대는 맵의 상자 대신 **설비 도해의 상세 모델을 그대로** 세웁니다.
  도해에서 고른 부위가 미니캠에서도 밝아집니다.
- 확대·축소는 버튼과 휠. 대상은 화면 가운데 레티클이 가리킵니다.
- 이 캠은 **설비정보 확인 탭에만** 둡니다. 상세 맵에는 두지 않습니다.

### 트랙 (구성안 §3)

"日" 토폴로지 · 단방향 시계방향. **44 m × 14 m, 곡선 반경 2.6 m.**
분기부 A(좌) · 합류부 B(우). 숏컷은 **A→B(상부 건너뛰기)** 이고 정차가 없습니다.

| 경로 | 길이 | 지나는 곳 |
|---|---|---|
| UPPER A→B | 49.6 m | P1 · P2 · P3 |
| SHORT A→B | 40.0 m | 없음 — 평소 최단경로 |
| LOWER B→A | 49.6 m | P4 · P5 · P6 |

우회(UPPER) / 최단(SHORT) = **+23.9%** → §3.3 조건 2(10~30%)를 만족합니다.
치수를 바꾸면 부팅 시 콘솔이 경고합니다.

### 구성안과 다르게 간 것 — 이유와 함께

**① 이상 구간을 하부 우측 곡선 → 숏컷 분기부로 옮겼습니다** (승인받음).
단방향에서 하변(P4~P6)에 닿는 길은 그 곡선 하나뿐이라 우회로가 아예 없고(§3.3 조건 1),
링을 가로지르는 현은 언제나 두 호보다 짧아 숏컷을 우회로로 쓰면 GOOD 이 오히려
짧아집니다(조건 2). 이상을 숏컷에 두면 둘 다 풀립니다.

**② 숏컷 방향은 A→B 입니다.** 반대(B→A)로 두면 상↔하 이송 job 이 숏컷을 한 번도
쓰지 않습니다 — 상부에서 실은 화물은 B 에서 내려가고 하부에서 실은 것은 A 에서
올라가므로 숏컷이 낄 자리가 없습니다(실측: 180초에 통과 5회).

**③ 배차는 job 큐 FIFO 입니다.** '가장 가까운 차량' 으로 두면 숏컷이 원리적으로 안
쓰입니다(실측: 통과 0회). 하부 픽업은 늘 상부에 있는 차가 더 가깝고, 하부에 들어온 차는
정차 없이 A 까지 갈 일이 없어 분기 판단 자체가 생기지 않습니다.

**④ 지표 2번을 '합류부 평균 대기' → '정체 시간 비율(%)' 로 바꿨습니다.** BAD 의 정체는
합류부가 아니라 이상 구간 바로 뒤에 생기고, GOOD 은 우회로 합류부 통과량이 늘어
합류부 대기만 보면 **GOOD 이 나쁘게** 나옵니다(측정: BAD 2.85초 vs GOOD 4.49초).
지표 자리는 두고 재는 대상을 바꿨습니다 — 어디서 생겼든 차가 자유속도의 1/4 아래로
서 있던 시간의 비율입니다.

> 참고: 구성안 §3.2 의 근거("상부↔하부 이송 job이 발생해야 경로 선택 문제가 성립함")는
> 사실과 다릅니다. 상↔하 이송은 경로 선택을 만들지 않습니다 — 픽업 지점에 닿기 전에
> 정차해 버리기 때문입니다. 선택을 만드는 것은 같은 층 안의 tool-to-tool job 과
> 복귀 트래픽이라, 물동량을 하부(장비) 쪽 75% 로 기울였습니다.

```
        ↓

        ↓

```

읽는 순서가 곧 데이터가 흐르는 순서입니다. 단 사이의 화살표가 그것을 보입니다.

### ④ 에이전트 — 보고 한 장뿐입니다

제품의 에이전트 패널에는 **감시 보고 카드 하나**만 있습니다. 예전 시안의 관찰 한 줄과
`데이터 수집 → 전처리 → 데이터 분석 → 교차 판정` 4단계 다이어그램은 제품에 없어
걷어냈습니다 — 단계는 화면이 아니라 **보고 문장**이 말합니다. 주기(관찰 → 정리 → 보고)는
그대로 돌고, 주기가 끝날 때 이 카드만 갱신됩니다.

미니맵 오른쪽 칸도 제품과 같이 **비워 둡니다**(제품도 `aria-hidden` 인 빈 슬롯입니다).
고른 대상의 상세는 맵 위 확대 패널이 보여 줍니다.

### ② 경고 감지

제품과 같은 규칙입니다 — 감지된 경고를 **종류별로 묶고**, 그룹마다 건수와 가장 최근
시각을 적고, 누르면 그 종류의 기록이 시간 순으로 펼쳐집니다. **CLEAR** 는 목록과 누적
건수를 비웁니다(맵에 떨어진 핀은 남습니다 — 제품의 라벨과 같은 취급).

제품의 경고 종류는 다섯입니다: 레일 벌어짐 · 레일 단차 · 이물질 충격 · 호이스트 과부하 ·
(분류 실패). 이 실측 로그에는 이·적재 계통 결함이 담기지 않아 **앞의 세 종류만** 재현됩니다.

### ③ OHT 건강도 — 점수를 어떻게 냈나

축 이름은 제품 그대로지만 점수는 지어내지 않았습니다. **그 채널의 평상시(중앙값)를 100점,
경고선을 0점**으로 놓고 그 사이를 잽니다(`score()`). 평상시보다 조용하면 100점에서 멈추고,
경고선을 넘으면 0점입니다. **곡선주행**은 이번 리그가 직선 왕복이라 관측 구간이 없어
제품과 같이 `- 데이터 없음`으로 둡니다.

### 제품과 다르게 남긴 것 — 이유와 함께

1. **좌측 3D 플레이어는 2.5D 아이소메트릭 그대로**입니다(요청 사항). 제품은 Unity WebGL
   `xdt-player` 입니다.
2. **맵 위 확대 보기 패널** 을 남겼습니다. 제품은 미니맵 오른쪽을 비워 두고 상세를 따로
   띄우지 않는데, 이 시안의 확대 패널은 채널별 파형을 함께 보여 주어 전시 설명에 쓰입니다.
   머리글은 제품의 표기(차량 상태값 / 이벤트 지점 상세 / 레일 구간 상세)를 씁니다.
3. **분석의 세 번째 지표**는 제품이 기울기(VNS-1 기울기 X · deg)인데, 이번 실측 로그에
   기울기 채널이 없습니다. 없는 값을 지어내는 대신 이 리그에서 레일 결함을 실제로 담고
   있는 **레이저 변위**를 그 자리에 두고, 카드에 그 사실을 적어 두었습니다.
4. **캔들 폭**은 제품이 60초 수신 버퍼에 2초 캔들입니다. 이 시안의 수신 버퍼가 실측 로그
   13.4초라 같은 비율로 **0.5초 캔들**입니다. 제품도 집계 구간에 따라 캔들 폭이 달라집니다.
5. **OHT-02 · OHT-03** 은 리스트에 세우되 `연결 끊김` 입니다 — 확보한 실측이 데모장치
   1대뿐입니다.

## 와셔 충격 — 발생 시점만 합성입니다

실물 리그는 벌어짐 → 충격 → 단차 순으로 감지 포인트가 놓여 있지만,
이번 캡처에는 **OHT 가 와셔를 밟고 지나가는 이벤트가 담기지 않았습니다.**

- `|acc|` 를 이동중앙값(±25ms)으로 고역통과시켜 확인하면 주행 4개 창 전부 임펄스 **0건**입니다.
  40~56% 구간의 진동 상승은 충격이 아니라 최고속(1.0 m/s) 주행 진동이었습니다.
- 와셔 임펄스는 마지막 창(`1785118086`)에서 OHT 가 **포트 A 에 정차한 동안에만** 잡혔습니다
  (t 4.75·4.94·7.13·7.30, 최대 1.71g). 그 창의 `OffsetMm` −1.52/−1.54 는 주행창의
  포트 A 정차값 −1.8~−1.6 과 일치하고(포트 B 는 +1.44~+1.57), 레일 장착 IMU 는 끝까지
  반응이 없습니다 — 충격원이 레일 중간이 아니었다는 뜻입니다.

그래서 그 캡처에서 **측정된 실제 충격 파형 350ms**(4.70~5.05s, 임펄스 2발)를 잘라,
주행 중 OHT 가 레일 67% 를 지나는 순간의 차량 IMU 구간과 맞바꿨습니다.
**파형은 실측이고 동시성만 합성입니다.**

접합이 매끄러운 근거 — 두 구간의 베이스라인이 사실상 같습니다:

| | AccX | AccY | AccZ | RMS | \|acc\| 중앙값 |
|---|---|---|---|---|---|
| 와셔 슬라이스 | +1.009 | −0.011 | +0.994 | 0.826 | 1.418 |
| 주행 중 같은 길이 | +0.960 | −0.010 | +0.995 | 0.799 | 1.381 |

AccX 만 0.05g 차이인데 주행 중 샘플간 변동(±0.1g)보다 작아 눈에 띄지 않습니다.
음압(`dba`)과 레일 IMU(`rvib`)는 손대지 않았습니다 — 레일 IMU 가 조용한 것은 실측 그대로입니다.

와셔 지점을 옮기려면 `tools/build_play_data.py` 의 `WASHER_AT` (기본 0.67) 한 줄만 바꾸면 됩니다.

## 교차판정 3축

| 축 | 소스 | 계산 | 경고 / 이상 |
|---|---|---|---|
| **트랙 (레일)** | `ad7.js` 10 kHz | 25ms 버킷 내 **진폭** `max − min` | 0.30 / 0.80 V |
| **차량 (휠)** | `vib.js` `RMS` 1 kHz | 25ms 버킷 **피크** | 0.90 / 1.10 g |
| **충격** | `vib.js` `AccX/Y/Z` 1 kHz | 합성가속도의 **순간 편차** `max − mean` | 0.20 / 0.40 g |

- 트랙축을 변위 **진폭**으로 잡은 이유: 벌어짐(포화)과 단차(레벨 전환)가 둘 다 '한 버킷 안에서 값이
  얼마나 벌어졌나' 로 걸리고, 단차 구간 **안에** 머무는 동안은(기준선만 낮을 뿐 진폭은 평상시)
  정상으로 남습니다. 기준선 편차로 잡으면 포트 B 쪽 구간이 통째로 이상이 됩니다.
- 충격축을 Z축이 아니라 3축 합성으로 바꾼 이유: 와셔 임펄스는 주행방향(X)에 가장 크게 실립니다
  (`AccX` 최대 2.97). 합성으로 보면 축 방향에 상관없이 임펄스를 잡습니다.
- 임계 근거는 **버킷 원값 분포**입니다(판정창 적용 전). 트랙축은 정상 구간이 유난히 조용해
  (p90 0.021, 전 구간 최대 0.06) 분위수와 최댓값 사이가 통째로 비어 있어 물리량으로 잡았습니다 —
  경고 0.30 = 정상 최대의 약 5배, 이상 0.80 = 실측 단차 레벨차(1.07)의 75%.
  결과적으로 **경고선을 넘는 버킷이 정확히 4개**(벌어짐 ×2 · 단차 ×2)뿐입니다.
  각 임계의 근거는 `index.html` 의 `AXIS` 객체 주석에 그대로 적어 두었습니다.
- 판정창은 1초(`JUDGE_WIN` 40버킷)입니다. 주행이 8.4초뿐이라 한 이벤트가 창 하나를 차지해
  주행 구간의 절반 남짓이 경고·이상으로 유지되는데, 결함 3개소를 일부러 밟고 지나가는
  데모라 그게 맞는 그림입니다.
- 코드 위치: 계산 `computeRanges()` (`D.disp` / `D.peak` / `D.shock`), 임계·라벨 `AXIS` 객체.

## 레일 위 위치(railT)

`OffsetMm` 은 태그마다 0 으로 리셋되지만 진행 방향의 부호가 그대로 붙어 있어,
같은 태그 안에서 `ΔOffsetMm` 을 더하면 부호까지 맞는 이동량이 됩니다. 태그 경계의 한 스텝만
실측 속도×dt 로 메웁니다. 속도만 적분하면 가감속 구간에서 왕로·복로가 약 140mm 어긋나는데,
이 방식은 같은 결함 지점이 두 통과에서 9mm 안으로 겹칩니다. 편도 약 2.27m, 사이클당 4.55m 입니다.

정차·진행방향·이적재 구간도 전부 실측에서 뽑습니다(`D.ops.port` / `dir` / `liftU` / `busy`).
예전 시안이 화면에서 지어내던 `DWELL` 상수는 없앴습니다 — 정차 길이는 이제 데이터가 정합니다.

## 우측 열 배치

```
┌──────────────────────────────────────┐
│ ③ 상태 / 판정      │ ④ 교차판정 (3축)  │   .pane-judge — 내용 높이, 전체 폭
├───────────┬──────────────────────────┤
│ ⑫ 레이더  │                          │
├───────────┤  ⑦ AI 모니터링 에이전트   │   .pane-split
│ (예약 자리)│                          │
└───────────┴──────────────────────────┘
  ← --dash-w →
```

세로 분할선의 x 는 `--dash-w` (⑫ 레이더 열 폭) 하나로 정해집니다. 예전에 레이더 오른쪽에
남던 빈 자리와 그 아래 에이전트 칸을 세로로 텄습니다 — 둘 다 '지금 무슨 일이 일어나는가' 를
보여주는 자리인데 가로선 하나로 갈라져 서로 다른 화면처럼 읽혔습니다.

`--dash-w` 는 `clamp(186px, 38%, 258px)` 입니다. **오각형이 이 열의 폭을 그대로 먹으므로
차트를 키우려면 여기를 넓히면 됩니다**(`#radar` 는 `width:100%` · `aspect-ratio:6/5`).
그만큼 오른쪽 에이전트 칸이 좁아지는데, 에이전트는 세로로 쌓는 배치라 폭에 여유가 있습니다.
px 로 못 박으면 좁은 화면에서 오른쪽이 먼저 굶으므로 비율로 잡되 위아래를 막아 둡니다.

왼쪽 아래는 **의도적으로 비워 둔 예약 자리**(`.pane-slot`)입니다. `#dashSpk` 가 그 안에
그대로 있으므로 `DASH_CH` 배열만 다시 채우면 채널 스파크라인이 여기로 돌아옵니다.

에이전트 패널은 두 덩어리입니다. 흐름은 위에서 아래로 한 줄입니다.

```
    [OPS ]──┐  ┌──[VIB ]
    [DBA ]──┼──┼──[RVIB]     센서 셀 3개씩 두 묶음이 가운데 등뼈로 모인다
    [SEG ]──┘  └──[AD7 ]
             │
       [신규 데이터 수집]
             │
       [전처리] … [교차 판정]   처리 단계는 위에서 아래로 쌓는다
             │
       [보고 내용 정리 중]
    ─────────────────────
       순찰 보고 · …
```

- **위** — 센서 셀은 `아이콘 · 채널 키 · 현재값` 한 줄 아래로 그 채널의 실측 계열을
  재생 위치에 맞춰 흘립니다(`AGF_SER`). 파형은 '어떻게 움직이는가' 만 말하므로 지금
  얼마인지는 숫자가 같이 말해야 합니다. 값은 머리줄 오른쪽에 붙여 셀 높이를 더 먹지
  않게 했습니다.
  단계 셀은 **한 줄**입니다 — `제목 · 지금 하는 일`. 두 줄로 나누면 셀 다섯 개가 세로를
  두 배 먹어 화면이 짧은 노트북에서 스크롤이 생깁니다.
- **아래** — 순찰 보고. 최신 1건만 남고 쌓이지 않습니다. 이 패널에서 유일하게 '읽는'
  블록이라 제목을 한 급 위로 잡습니다(최대 18.5px).
  **자리를 미리 잡아 둡니다**(`min-height`) — 첫 보고 전에는 한 문장뿐이라 이 블록이 확
  쪼그라들고, 첫 보고가 들어오는 순간 위 다이어그램이 통째로 밀려 올라가 화면이
  덜컹입니다. 채워졌을 때보다 조금 넉넉하게 잡아 아래가 남아도 그대로 둡니다.

**셀은 작게, 선은 길게.** 셀을 키우고 선을 짧게 두면 상자만 줄줄이 붙은 표처럼 보입니다 —
다이어그램은 '무엇이 무엇으로 흐르는가' 가 읽혀야 하고 그건 선이 만듭니다. 선
(`--agf-run` / `--agf-crow` / `--agf-spine`)은 `flex:none` 이라 먼저 자리를 잡고, 셀은 남는
세로를 나눠 먹으므로 **선을 늘리면 셀이 그만큼 알아서 작아집니다.**
단, 셀 높이를 낮추면 스파이크 라인이 먼저 사라집니다(칩 = 머리 + 파형인데 머리가 고정이면
줄어드는 건 파형뿐). 그래서 칩 아이콘(`--agf-cic`)도 셀 높이를 따라 같이 줄입니다.

### 단계 문구는 계속 바뀝니다

`STEP_DETAIL` 은 그 단계가 **끝났을 때** 남는 결론이고, `STEP_TICK` 은 그 단계가 도는 동안
순서대로 지나가는 중간 상태입니다. 한 단계가 1초 안팎이라 300ms 마다 넘기면 세 마디가
지나갑니다. 각 배열의 **마지막 마디가 곧 `STEP_DETAIL`** 이라, 단계가 끝나면 결론이 그대로
남습니다. 문구가 갈릴 때마다 `.turn` 으로 한 번 떠오릅니다 — 순간이동하듯 갈리면 바뀐 줄도
읽히지 않습니다.

### § 흐름 시계 — 움직임은 전부 rAF 루프가 만든다

빛의 이동도, 테두리를 도는 각도도, thinking 점의 오르내림도 **CSS 애니메이션(`@keyframes`)이
아니라** `tickFlow(dt)` 가 매 프레임 커스텀 속성을 갱신해서 만듭니다. 이유:

1. 가상요소(`::before` / `::after`)에 건 애니메이션이 환경에 따라 아예 만들어지지 않아
   화면에서 흐름이 통째로 멈춰 보이는 일이 있었습니다. 재현할 수 없는 환경 변수를
   데모의 핵심 연출이 붙들고 있을 이유가 없습니다.
2. `@property` 로 등록한 커스텀 속성을 애니메이션하는 방식은 등록 여부와 가상요소 지원이
   브라우저마다 달라 더 불안합니다.
3. 여러 줄기가 한 시계를 쓰므로 위상이 어긋나지 않고, 맵 캔버스와 같은 루프라 프레임이
   갈리지도 않습니다.

CSS 로 넘어가는 값은 **0~1 위상**(`--beam-p` / `--scan-p`)과 **각도**(`--agf-ang`), 그리고
점의 밝기·높이(`--d1o` … `--d3y`)뿐이고, 실제 이동은 CSS 가 `transform` 으로 처리합니다.
주기는 `FLOW_MS` 한 곳에 모여 있습니다 — 갈비뼈 620 / 파형 흐름 2100 / 등뼈 3100 /
연결선 520 / 러너 2200(진행 중 1400) / 점 1250 ms.
REC(과거 재생) 중에는 이 시계가 멈추고 남은 빛도 지웁니다.

> 헤드리스 크롬을 `--virtual-time-budget` 으로 찍으면 CSS 애니메이션은 시간이 0 으로
> 압축돼 `getAnimations()` 에조차 안 잡힙니다(새로 만든 일반 요소도 마찬가지).
> 이제는 rAF 기반이라 `FLOW.t` 를 직접 넣고 `tickFlow(0)` 을 부르면 원하는 위상을
> 그대로 캡처할 수 있습니다.

### 모션 — 한 줄기 빛

마디가 줄지어 행진하면 눈금자처럼 보입니다. **한 선에 하나씩만**, 빛 한 줄기가 선을 타고
미끄러지는 편이 '값이 지나간다' 로 읽힙니다. 양끝을 알파로 0 까지 빼서(`--beam-y` /
`--beam-x`) 끝이 뚝 끊긴 막대가 아니라 빛으로 보이게 했습니다.

**움직임은 `transform` 이고, 그걸 미는 것은 CSS 애니메이션이 아니라 rAF 루프입니다**
(§ 흐름 시계). 상자(`overflow:hidden`) 안에 상자보다 한 줄기 길이만큼 더 긴 띠를 두고,
띠의 맨 앞 한 줄기 구간에만 빛을 칠한 뒤(`background-size` + `no-repeat`) 띠를 자기 길이의
0~100%(= 상자 길이 + 한 줄기)만큼 밉니다. 빛이 뒤로 빠져나간 바로 그 순간 앞에서 다시
들어와 이음매가 보이지 않습니다. 미는 값은 `--beam-p`(0~1) 하나뿐입니다.

빛은 **항상 바탕선 위에 겹치는 별도 층**입니다. 바탕선 자체를 빛으로 바꾸면 빛이 없는
동안 선이 통째로 사라집니다.

| 선 | 바탕 | 빛 (상자 / 띠) | 언제 |
|---|---|---|---|
| 갈비뼈 | `.agf-chip::after` | `.agf-rib` / `::before` | **항상** (셀 → 등뼈, 좌우 방향 반대) |
| 등뼈 → 수집 셀 | `.agf-cells::before` + `.agf-link::before` | `.agf-spine` / `::before` | **항상** (아래로) |
| 단계 사이 | `.agf-link::before` | `.agf-link` / `::after` | 지금 값이 지나가는 선만 |

등뼈는 센서 묶음 안에서 끝나지 않고 **수집 셀 문턱까지** 내려갑니다
(`bottom: calc(-1 * var(--agf-run) - 1px)`). 센서 묶음에서 한 번, 연결선에서 또 한 번 따로
흐르게 두면 빛이 중간에서 끊겨 '두 번에 나눠 보낸다' 로 보입니다.

**센서 → DB 는 늘 살아 있습니다.** 센서가 값을 멈추는 순간은 없습니다. 요원이 방금 받은
구간을 분석하는 동안에도 다음 값은 계속 들어오므로, 센서 점등(`chipLive`)과 DB 로 들어가는
빛은 순찰 주기와 무관하게 항상 돕니다. 예전에는 관찰 구간(`.stream`)에만 켜 두었는데,
주기의 40%인 분석 구간마다 센서가 통째로 꺼져 '데이터가 끊긴' 것처럼 읽혔습니다.
멈추는 것은 REC(과거 재생)뿐입니다. 이제 `.stream` 이 뜻하는 것은 상태 한 줄의 색 하나뿐입니다.

갈비뼈와 등뼈의 상자는 **실제 요소**입니다 — 상자와 띠 두 겹이 필요한데 가상요소는
자기 가상요소를 가질 수 없어서입니다(`buildAgentFlow` 가 넣습니다). 등뼈는 절대배치라
그리드 칸을 차지하지 않으므로 칩 여섯 개의 `nth-child` 번호도 그대로입니다.

구간 길이가 제각각(갈비뼈 23px / 등뼈 150~330px / 연결선 10~16px)이라 지나가는 시간을
따로 잡아 속도를 70~90px/s 로 맞춥니다(`FLOW_MS`).
여섯 줄기는 셀마다 위상을 0.17 씩 어긋나게 받아 조금씩 늦게 흐릅니다 — 딱 맞아떨어지면
기계 눈금처럼 보입니다.

단계 연결선은 `:has(+ .agf-step.on)` 으로 '바로 다음 형제가 진행 중인 셀' 을 집어
그 선에만 흐름을 켭니다. 지나온 선은 흐름을 멈추고 자국(`--brand-a32`)만 남깁니다.

**테두리를 도는 빛**(`agfRun`) — 원뿔형 그러데이션을 테두리 두께만 남기고 마스크로 도려낸
뒤 `@property --agf-ang` 를 돌립니다. 색만 바꾸면 그 셀이 '켜져 있다' 는 것만 말하고
'일하는 중' 이라는 말은 못 합니다. **1px 테두리에 흐린 호를 돌리면 움직이는지가 안 보입니다** —
링을 2px 로 세우고 호를 짧고 밝게(밝은 끝을 흰빛에 가깝게) 잡아야 '지나간다' 로 읽힙니다.

세 곳에 씁니다:

- **센서 셀 6개** (`.agf-chip::before`, 2.2s) — 값을 멈추지 않으므로 항상 돕니다.
  여섯 셀이 조금씩 어긋난 위상을 받아 한 줄기가 셀을 차례로
  훑고 지나가는 것처럼 보입니다. 파형 위로도 흐름 한 줄기(`.agf-scan`)가 왼쪽에서
  오른쪽으로 지나갑니다 — 파형이 '무엇이' 라면 이건 '지금도' 입니다.
- **`신규 데이터 수집` 셀** (`[data-s="0"]:not(.on)::before`, 2.2s) — **항상 켜져 있습니다.**
  센서 값이 실시간으로 들어오는 한 이 단계는 쉬지 않으므로, 다른 단계처럼 '차례가 와야
  켜지는' 셀이 아니라 센서 셀과 같은 상시 상태로 둡니다.
- **진행 중인 단계 셀** (`.agf-step.on::before`, 1.4s) — 호가 더 길고 빠르고 밝아
  '지금 판단하는 곳' 이 여전히 제일 눈에 걸립니다. 수집 셀이 실제로 그 차례가 되면
  이 규칙이 상시 러너를 덮어씁니다.

**좌표 계산이 없습니다.** 센서 묶음도 단계 셀도 가운데 정렬이라 등뼈(`.agf-cells::before`)와
연결선(`.agf-link::before`)이 전부 `left:50%` 에 섭니다. 갈비뼈는 셀 안쪽 모서리에서
`--agf-spine / 2` 만큼만 뻗으면 등뼈에 닿습니다. 셀 개수나 크기를 바꿔도 CSS 만 고치면 되고
JS(`buildAgentFlow`)는 그대로입니다.

센서 셀은 `grid-auto-flow:column` 입니다. 행 우선으로 채우면 왼쪽 묶음이 OPS·SEG·RVIB 로
뒤섞입니다.

**셀 폭은 패널을 다 채우지 않습니다.** 양옆에 여백이 있어야 다이어그램으로 읽힙니다.

### 세로 치수는 패널 자기 높이 기준입니다 (스크롤 방지)

세로 치수를 화면 높이 **구간**(`@media max-height`)으로 나누면 경계 바로 위 해상도에서
한 단계 큰 값이 그대로 적용돼 스크롤이 생깁니다(뷰포트 865 에서 실제로 52px 넘쳤습니다).
브라우저 툴바 · 북마크바 · 작업표시줄에 따라 같은 모니터에서도 뷰포트가 100px 넘게
달라지므로 구간으로는 못 막습니다.

그래서 `.agent-bd{container-type:size}` 를 걸고 모든 세로 치수를 `clamp(하한, N cqh, 상한)`
으로 잡습니다. `1cqh` = **이 패널이 실제로 받은 높이**의 1% 입니다.
`vh` 는 못 씁니다 — 앱 전체에 `zoom` 을 쓰고 있어 `vh` 가 zoom 이전 뷰포트를 보는 탓에
확대 화면에서 값이 부풀려집니다.

**남는 세로는 센서 묶음과 단계 셀이 4 : 6 으로 나눠 먹습니다**(`.agf-cells{flex:5}` /
`.agf-step{flex:1}` × 5, 연결선과 보고는 `flex:none`). 스파크라인은 셀이 높다고 더 읽히지
않지만(가로로 긴 편이 낫습니다) 단계 셀은 높아질수록 글씨와 아이콘에 숨통이 트입니다.
화면이 짧아지면 같은 비율로 줄어들다가 각자의 하한에서 멈추고, 그 뒤에야 스크롤이
생깁니다 — 1080 급에서 90px 가까이 이 두 블록이 흡수하므로 툴바 · 북마크바를 켜도
스크롤이 생기지 않습니다.

행 높이가 `1fr` 이라 등뼈 시작점은 px 로 못 적고 `(100% − 간격 2개) / 6` 으로 잡습니다.
행은 반드시 `minmax(0, 1fr)` 이어야 합니다 — `1fr` 만 쓰면 행의 자동 최소 크기가
min-content 라, 셀 안 캔버스의 최소 높이가 그대로 바닥이 되어 행이 컨테이너보다 커지고
아래 단계 셀 위로 넘칩니다.

`cqh` 에 계수만 곱하면 큰 화면과 작은 화면의 비가 고정됩니다(1080:900 이라야 1.34배).
선 길이와 보고 자리는 `calc(N cqh − 상수)` 로 잡아 기울기를 세웠습니다 — 큰 화면의 여유는
지키면서 좁은 화면에서는 훨씬 빨리 줄어듭니다.

## ⑨ 센서 상세 패널 — 무엇을 골랐든 같은 형식

맵에서 OHT 를 클릭하든 레일 구간을 클릭하든, 패널 맨 위(`#sideSum`)는 **그 대상의 실측
요약 한 줄**이고 그 아래(`.seg-stat`)가 통계 그리드, 그 아래가 채널 파형입니다.
다른 것은 단위뿐입니다 — 레일은 '구간', OHT 는 '사이클'.

| | 요약 한 줄 | 통계 그리드 |
|---|---|---|
| OHT | 사이클 4.55m · 13.4s · 최고 1.06m/s · 감지 지점 3개소 통과 | 진동 피크 / 순간 충격 / 최고 속도 / 사이클 주행 · 시간 / 통과 감지 지점 |
| 레일 구간 | 구간 길이 0.72m · 통과 0.8s · 평균 0.96m/s · 벌어짐 결함 포함 | 진동 피크 / 변위 진폭 / 충격 / 최고 속도 / 구간 길이 · 통과 시간 / 구간요약 |

OHT 쪽에는 예전에 `스파크라인과 우측 실시간 수치가 함께 흐릅니다` 라는 **UI 사용법**
한 줄만 있어서, 같은 자리에 레일은 정보가 있고 OHT 는 없는 상태였습니다.
